**Run date:** 2026-05-16
**Outcome:** report shipped after three rounds of editorial revision and one remediation patch on the Airtable write-back.
**What this file is:** durable patterns from that run, written down so the next Lois engagement doesn\'t hit the same walls.

## 1. Pain hierarchy — read every signal, weight them honestly

The questionnaire produces several pain-related fields. They can disagree, and the wrong one usually shouts loudest:

| Field | What it is | How to weight it |
|---|---|---|
| **Pain narrative** (free text) | The client\'s own words. | **Strong.** This is the qualitative signal. |
| **Biggest frustration** (multi-select) | Tick-boxes from a fixed list. | **Weak unless backed by narrative or quantification.** Easy to over-tick. |
| **D-section quantifiers** | hrs/wk, %, $ figures conditional on the frustration choice. | **Strong when not "Don\'t know"** — a real number means the pain is felt. |
| **Hated weekly task** (free text) | The specific thing they wish they didn\'t have to do. | **Very strong.** Single best signal of where they feel friction. |
| **Future state vision** (free text) | What they want instead. | **Very strong.** Tells you the *outcome* they\'re buying. |
| **Confirmed pains** (checkbox list) | "Which of these match your experience?" | **Strong** — explicitly confirmed, often stronger than Biggest frustration. |
| **Pain tags (multi)** / **Pain tag (derived)** | Formula output. | **Useful for matching, not for weighting.** Order is not priority. |

**The rule:** derived tags surface candidates; narrative + hated task + future state set priority. Confirmed pains beat tick-boxes.

### What this looked like on Luan

The matcher emitted `invoicing, comms` as derived tags. First-pass Lois (me) treated invoicing as primary because it was listed first. **Wrong call.** Every qualitative field said comms:

- Pain narrative: *"Email response to clients with solutions"*
- Hated task: *"Emails"*
- Future state: *"No longer responding to clients\' issues as they have already been addressed"*

And the *Confirmed pains* field carried a different signal entirely — *"Staff spend time re-entering the same info across systems"* (`manual-entry`) — which v1 missed entirely. The corrected hierarchy that landed in v3:

1. **comms** (very strong)
2. **manual-entry** (strong, confirmed)
3. **knowledge-sharing** (medium, in multi-select)
4. **invoicing** (weak, tick-box only, "Don\'t know" on quantifier)

## 2. The editorial test — "when did the client actually say this?"

Before each recommendation lands in the report, run the test: **can you quote the source field?** If you can\'t, the recommendation isn\'t grounded — it\'s a guess dressed up as analysis.

This is the single most useful check Linh runs on a Lois draft. Internalise it.

### What happens when you skip it

In v1 of Luan\'s report, I recommended five tools. Linh asked three questions:

- *"When did Luan say invoicing was a pain?"* — once, in a tick-box, with no narrative.
- *"When did Luan say scheduling was a problem?"* — he didn\'t. I made it up to justify Calendly.
- *"How does PandaDoc help him? Draft docs and emails?"* — no. He didn\'t mention documents.

**Three of five recommendations were ungrounded.** The cure was tightening to one well-grounded tool (Notion) + one explicitly-conditional pair (Xero + Chaser) + a deeper digital-employee section.

## 3. Assumption-handling — if you must infer, label it

Sometimes the response is sparse and an inference is the right call. **That\'s allowed.** What\'s not allowed is presenting the inference as the client\'s stated pain.

### The pattern

When the report rests on an assumption:

1. State the assumption explicitly in the recommendation\'s **Why this for you** field.
2. Tie it to a Discovery Week 1 confirmation step.
3. Describe what changes if the assumption is wrong.

### Worked example from Luan v3

Luan listed "CommSee" in *Top tool 3* but said nothing about issues with it. I designed a **Client Activity Concierge** agent to address his confirmed manual-entry pain. The natural framing would have been "CommSee Data Concierge" — but he never named CommSee as the bottleneck.

The generic-naming pattern fixes this:

> *"Watches your Outlook for client-related signals... and drafts the corresponding log entry into your practice-management system for your approval. **We assume the destination is CommSee based on your top-tools list; we\'ll confirm in Discovery Week 1, and if it\'s actually a different system, the agent\'s destination flexes — its inputs and your approval step don\'t.**"*

The bolded sentence is the labelled assumption. It buys the same clarity as a fully-grounded recommendation without overclaiming.

### Phrases that signal assumption (use these)

- *"We assume X based on Y; we\'ll confirm in Discovery Week 1."*
- *"Your response didn\'t explicitly say X, but Z suggests..."*
- *"If we\'ve read this wrong, tell us — we\'d swap for W."*
- *"Conditional on — only activated if Y is confirmed at Day 30."*

### Phrases that disguise assumption (avoid)

- *"You said X."* (when they didn\'t).
- *"Your stated pain is X."* (when X isn\'t in any field).
- *"As you mentioned, X."* (when they didn\'t mention it).

## 4. "Lean on agents, not tools" — the negative-recommendation pattern

When the client is already on a capable stack and their tech appetite is Simple, the right report often recommends **less software, not more**. Selling fewer tools doesn\'t weaken the report — it strengthens trust and credibility, and it puts the weight where Rogue Night actually adds value: the digital employees.

### When to lean this way

- Existing stack already covers most basics (M365 / Google Workspace / dedicated vertical CRM).
- Tech appetite = Simple (Plug-and-play, minimal integrations).
- Solo or very small team.
- Pain is about **using what they have better**, not about a missing tool.

### How it shows up in the report

- The recommended stack shrinks to one or two confidently-grounded tools.
- The cull section grows — explain explicitly what you\'re *not* recommending and why.
- The digital-employees section becomes the main work, not a postscript.
- The cost section starts at $0/mo baseline, not "$X for the new stack."
- The cover pitches "fewer tools / [N] digital employees" not "[N] tools across [Y] weeks."

### Worked example from Luan v3

Cover: **"Fewer tools. Three digital employees."**
Exec summary: *"You don\'t need more software. You\'re already on capable tools. What\'s missing is somebody working those tools alongside you."*
Recommended stack: Notion (free) + conditional Xero+Chaser.
Digital employees: 3 + 1 conditional, deeply detailed.

The pitch lands better than v1\'s five-tool stack did, and it\'s defensible against the editorial test on every line.

## 5. Operational gotchas (the kind that crash scripts)

### Phase field must be a canonical single-select value

The Airtable Phase field is a single-select. Writing strings like `"Day 30+ (conditional)"` or `"Week 12 (optional)"` to it returns 422 and crashes `write_back.py` mid-loop, leaving Airtable in a half-written state.

**Fix:** v2 `write_back.py` validates Phase before any POST. Canonical values are `Day 0`, `Day 1`, `Day 7`, `Day 14`, `Day 21`, `Day 30`, `Day 60`, `Day 90` (plus `Week N` variants if the Airtable schema allows). Conditional or explanatory framing belongs in `Plan / tier`, not Phase.

### Tool record IDs aren\'t optional in practice

v1 made `tool_id` optional and left Tool / Tool Name / Category empty when absent. That produces ugly half-populated Recommendations rows.

**Fix:** v2 `write_back.py` auto-looks-up `tool_id` from `tool_name` via the Tools table when missing. Callers only need to pass the tool name.

### Reports row needs Label + Sent date populated at creation

v1 created the Reports row with only `Version` + `Status`, requiring a follow-up patch script to add Label and Sent date.

**Fix:** v2 fetches the Response\'s Business name and builds `Label = "<Business> — AI & Automation Strategy"`. Accepts `sent_date` in `report_meta.json`, defaults to today.

### Windows cmd `set VAR=value && cmd` captures trailing whitespace

`set AIRTABLE_BASE_ID=appXYZ && python ...` sets `AIRTABLE_BASE_ID` to `"appXYZ "` (with trailing space), which becomes `%20` in the URL path and Airtable returns 404.

**Fix:** always quote: `set "AIRTABLE_BASE_ID=appXYZ"`. The quoted form strips whitespace cleanly.

### Sandbox proxy blocks api.airtable.com

If you\'re running Lois inside Cowork (or any sandboxed Claude), outbound HTTPS to `api.airtable.com` is blocked by the proxy (403 on CONNECT). Pattern: **prep the artifacts in-sandbox, run the write commands from Linh\'s machine.** Same applies to `roguenight.com.au` verification.

### Render fidelity fallback chain

Production renders should use Playwright. Sandbox installs of Playwright + Chromium time out at 45-second bash limits (~200MB total download). Fallback order:

1. **Playwright** (best) — handles CSS grid + @page rules + backgrounds cleanly.
2. **WeasyPrint** (acceptable for review) — may stretch white grid-row backgrounds across page breaks, but layout otherwise good.
3. **Chrome → Ctrl+P → Save as PDF** (manual fallback) — A4, background graphics on.

Always document which renderer produced the PDF that was sent.

## 6. The shipping checklist

Before any report leaves Linh\'s hands:

- [ ] Every recommendation passes the editorial test (can you quote the source field?)
- [ ] Every assumption is explicitly labelled in the report body
- [ ] Pain hierarchy is correct (re-read narrative + hated task + future state + Confirmed pains)
- [ ] Voice rules: no SME, no AI-generated, no Brisbane, no founder name, no AI analyst
- [ ] Pricing is current AU 2026 (cross-check against vendor pages, especially Xero)
- [ ] Phase values are canonical
- [ ] Tool names match Airtable Tools table exactly (so `tool_id` lookup succeeds)
- [ ] Renderer is documented (Playwright / WeasyPrint / manual)
- [ ] Email body voice-checked
- [ ] If sending pre-payment, the email or report explicitly acknowledges the engagement state
